The side browser is a single Qt WebView loaded by `WebSurface.qml`. By default, a new successful `submit_to_chatbox` tool event with an HTTP(S) URL in the active session expands it automatically; history replay, background sessions, ordinary assistant text and other tools leave it closed. A user can also click an already-delivered URL card to open the pane. Repeated submissions replace the current URL, or reload the same page. Closing destroys the view. URL cards have three context actions: open in the default system browser, copy the URL, and attach the URL to the current chat while keeping its draft. Attachment chips keep their URLs when sent or restored from history.

In the Python edition, **Settings → Agent → Umeko Desktop** controls automatic opening after submission and whether webpages use the embedded preview or the system default browser. These preferences apply to both HTTP(S) URLs and local HTML files. With automatic opening off, deliveries stay in chat and clicking a card opens them. The external-browser option skips WebView creation immediately and skips native WebView initialization on the next startup, which helps on machines where WebView2 crashes. After switching back to embedded preview, restart Umeko to use it. Markdown, text and source-code previews use the native document pane in both modes. Agents can inspect `settings.get` and partially update `desktop.configure`; see `runtime/umeko-docs/settings.md`.

`PidMotion` controls the panel width, including closing to zero. The native view is hidden during motion and while a modal overlay is displayed. It stays alive during ordinary navigation and overlays, keeping back/forward history, and is destroyed when dismissed or when the session changes.

On Linux the base package carries only the small Qt WebView frontend. The WebEngine backend, renderer helper, resources and Qt dependencies are a separate, pinned ZIP. `runtime/webview-component.json` identifies its immutable resource tag, size and SHA-256. Both editions share the per-user component directory and validate its Qt version before loading it at startup. Source development can override that directory with `UMEKO_WEBVIEW_COMPONENT_DIR`.

When a URL is submitted on Linux without the engine, the submit tool's response carries the component instructions: the official release page, direct ZIP URL, checksum, destination and activation JSON. The Agent verifies the ZIP and installs it with its existing tools. The user restarts Umeko when convenient, so running Agent work continues uninterrupted.

Build the component with `python scripts/webview_package.py --qt-root /path/to/Qt/6.10.2/gcc_64 --engine release-assets/webview --registry runtime/webview-component.json`. Update the same registry in both editions whenever the resource tag changes. The manual `webview-component.yml` workflow checks the pinned registry before publishing a separate prerelease resource tag, which app update checks skip.

The Python build stages the WebView frontend files from the checksum-verified matching PySide wheel; the full PySide Addons distribution is not needed. The tray listens to the main window only, so the global event filter never wraps transient Chromium objects.

The same panel shows local Markdown, source code and plain-text artifacts through `DocumentSurface.qml` and the bounded background `DocumentPreview` reader. This mode works without WebView and the Linux component. A shared left divider resizes web/document previews directly, and opening/closing uses PID motion. First focus on the web address field selects its entire URL. See `chatbox-media.md` for limits, cancellation and fallback behavior.
