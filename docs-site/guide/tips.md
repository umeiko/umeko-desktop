# 可以这样问我 {#things-to-try}

不必记住所有入口。告诉我目标，再给出范围和限制，我就更容易帮上忙。

## 第一次来到项目 {#new-to-a-project}

> 先给这个项目画一张目录地图，解释怎么启动和验证。只读，不要修改文件。

## 想批量处理任务？ {#a-batch-of-tasks}

> 把这三份文档分别交给子智能体检查，再由你整理一份共同问题清单。先不要修改原文。

可以并行的事情交给不同助手；最终结论和验证仍由主 Agent 汇总。[看看委派方式](./subagents)。

## 你知道吗？我也可以改变软件外观 {#did-you-know-i-can-change-the-app-s-look}

> 生成一个纯白色主题并应用！文字要清楚，保留当前人物。

主题与角色分开管理，也可以导出人物制作 Skill 做自己的形象。[外观设置](./appearance)。

## 给我装点新本领 {#give-me-a-new-skill}

> 找出适合这个任务的 Pi 扩展，先解释来源和作用，得到我同意后再安装到当前内嵌 Pi。

Skill 是任务指南，扩展可以增加工具，MCP 连接外部服务。先分清要哪一种。[扩展指南](./skills)。

## 做出来了，就让我看见 {#made-something-show-me}

> 把报告保存成 Markdown，并通过 submit 展示；图表也直接发到聊天。

不用自己追着路径找文件。[产物预览](./artifacts)。

## 方向不对？随时拉我一把 {#going-the-wrong-way-steer-me}

> 先停下界面美化，优先修复登录失败；不要改数据库结构。

运行中可用 Ctrl+S 优先介入，Enter 则留作后续消息。把「做什么」和「别改哪里」一起说清楚。

## 我的插件出问题了？让我先看看 {#a-plugin-broke-let-me-inspect-it}

> 检查当前 Pi、扩展和网络设置，先解释可能原因，不要重装或清空配置。

版本、错误详情和稳定复现步骤，比一句「坏了」更有用。[反馈清单](../troubleshooting#report-a-problem)。

## Token 要花在刀刃上 {#spend-tokens-where-they-matter}

> 先列一个简短方案，改最小必要范围；如果需要扩大任务，先解释原因。

上下文精简时，模型更容易抓住重点。长任务把决定写进文档，阶段完成后再压缩会话。并发助手和重试都可能产生额外模型费用。
